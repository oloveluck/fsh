fsh: FHIR Shorthand for Racket🔗

A FHIR Shorthand compiler. You write profiles, extensions, value sets, code systems and example instances in .fsh files, the way you would for SUSHI; raco fsh check compiles them and validates every example against the profiles, pointing at the FSH line behind each problem. It also goes the other way (FHIR JSON to FSH), and a .fsh file is a Racket module whose resources a program can use.

Held to real guides: IPS 2.0.1, mCODE 4.0.0, Da Vinci Plan-Net 1.2.0 and Da Vinci HRex 1.1.0 compile from their own sources with no errors, their published packages are reproduced resource for resource but for a handful of named differences, and mCODE’s 283 examples validate against the profiles compiled here, as they do against the published package. Part of the fhir family.

1 Quick start🔗

1. Install. The packages are not on the Racket package server yet; clone the repositories side by side and install from source:

raco pkg install --link --auto fhir/fhir fhir/fhir-spec fhirpath vcl fhir/fhir-tx fhir/fhir-validation fsh

2. Write a project. A directory with a sushi-config.yaml and .fsh files under input/fsh/ (the SUSHI layout):

# ig/sushi-config.yaml

id: example.bp

canonical: http://example.org/bp

fhirVersion: 4.0.1

dependencies:

  hl7.fhir.us.core: 6.1.0

// ig/input/fsh/bp.fsh

Alias: $loinc = http://loinc.org

 

Profile: ScreeningBloodPressure

Parent: Observation

Id: screening-blood-pressure

* status = #final

* code = $loinc#85354-9 "Blood pressure panel"

* subject 1..1

* component ^slicing.discriminator.type = #pattern

* component ^slicing.discriminator.path = "code"

* component ^slicing.rules = #open

* component contains systolic 1..1 and diastolic 1..1

* component[systolic].code = $loinc#8480-6 "Systolic blood pressure"

* component[systolic].value[x] only Quantity

 

Instance: reading-1

InstanceOf: ScreeningBloodPressure

Usage: #example

* status = #final

* subject = Reference(Patient/ann)

* component[systolic].valueString = "high"

3. Check it.

$ raco fsh check ig/

ig/input/fsh/bp.fsh:22:3: fsh validate error: instance reading-1: Observation.component.value[x]:

    valueString is not allowed in slice 'systolic' (value[x]: Quantity)

    (constrained by profile ScreeningBloodPressure at ig/input/fsh/bp.fsh:15:3)

22 | * component[systolic].valueString = "high"

   |   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

fsh check: 1 examples, 1 with errors; 1 error(s), 0 warning(s)

The error sits on the instance rule that wrote the bad element and names the profile rule it breaks. Fix the line (valueQuantity = 140 ’mm[Hg]’), run again, exit 0. Then raco fsh ig/ writes the resources to ig/fsh-generated/, and raco fsh ig/ –pack writes the FHIR NPM package.

2 Writing FSH🔗

The language is SUSHI’s; the reference is the FSH specification. In brief: an entity (Profile, Extension, Instance, ValueSet, CodeSystem, Invariant, RuleSet, Mapping, Logical, Resource, Alias) is its keyword lines followed by rules, one per *:

rule

  

example

cardinality and flags

  

* subject 1..1 MS

assignment (a pattern; add (exactly) for a fixed value)

  

* code = $loinc#85354-9 "Blood pressure panel"

binding

  

* category from ObservationCategoryCodes (required)

type

  

* value[x] only Quantity or CodeableConcept

slicing

  

* component contains systolic 1..1 and diastolic 1..1

invariant

  

* obeys bp-1

rule set

  

* insert CommonMetadata

anything else, through the element definition

  

* code ^short = "What was measured"

Everything SUSHI accepts for R4 and R5 is accepted here: indented rules (path context), parameterized rule sets, reslicing, extension scaffolding, logical models and custom resources, mappings, and the dependencies named in sushi-config.yaml, which are found in fhir-spec as <id>-<version>.tgz.

3 Using it🔗

3.1 Command line🔗

raco fsh check ig/

  

compile; validate every example against the project's profiles; problems on their FSH lines

raco fsh check ig/ –capability <id>

  

also what a server generated from that CapabilityStatement would not do (needs fhir-server)

raco fsh ig/

  

compile every .fsh to ig/fsh-generated/<Type>-<id>.json

raco fsh ig/ –pack [out.tgz]

  

also write the FHIR NPM package

raco fsh file.fsh

  

one file, with the default canonical and R5

raco fsh –decompile sd.json

  

FHIR to FSH

Flags: -o <dir>, --fhir-version 4.0.1|5.0.0, --canonical <url>, --snapshot (also generate snapshots), --format text|json|outcome (how problems are reported: text with a caret on stderr, or JSON or a FHIR OperationOutcome on stdout for a program). Exit codes: 0, 1 on an FSH error, 2 on usage.

A package written by --pack is served by raco fhir-server serve-ig out.tgz –capability <id> (the fhir-server package), with its dependencies resolved from fhir-spec.

3.2 As a module🔗

(require "bp.fsh") compiles the file when the program compiles; a parse or compile error is positioned in it. The module provides compiled (the FHIR resources as jsexprs), resources (typed nodes) and document (the entity ASTs). racket bp.fsh prints the JSON. A single file is compiled for R5 with the default canonical; use compile-project for a project with a config.

(require (only-in "bp.fsh" [compiled clinic])
         fhir/data-source (only-in fhir/conformance/operations ensure-valid))
; the profile is resolvable by url, because requiring the module registered it
(parameterize ([current-data-source (resources->data-source clinic)])
  (ensure-valid reading #:profile "http://example.org/StructureDefinition/screening-blood-pressure"))

3.3 From Racket🔗

(require fsh/compile fsh/project fsh/check fsh/decompile)
(fsh->fhir text)                                   ; source -> (listof jsexpr)
(define p (compile-project "ig/"))                 ; with its sushi-config.yaml
(project-artifacts p)                              ; the resources
(project-diagnostics p)                            ; every problem, positioned
(check-report-diagnostics (check-fsh-project "ig/"))
(fhir->fsh sd)                                     ; jsexpr -> FSH text

3.4 Maps in a project🔗

A project may also hold .map files in the FHIR Mapping Language (the fml package, loaded when present). Their StructureMaps join the package, and check checks each map against the project’s structures and transforms the examples of its source structure, validating the results against the target; findings are positioned in the map. A Logical: model is registered as a type, so an Instance: of it builds like any resource. The worked project is fhir-examples/examples/intake-maps; the fml document walks through it.

4 In an editor, for an agent🔗

fsh/support is what the family’s language server (fhir-lsp) and MCP server (fhir-mcp) load for FSH: a document’s diagnostics with its project, the project’s files, the outline, hover (an element path in the base type; a name’s declaration), go to definition across the project, completion (keywords, Parent and InstanceOf types and profiles, value sets after from, rule sets, invariants, the base type’s elements at a path, flags), and the tools fsh_check, fsh_compile and fsh_decompile. It is a fhir/lang/support value; the hubs know no FSH.

5 Limits🔗

Measured against the IGs’ published packages: IPS 2.0.1 pairs 114 resources, 94 identical, 108 with all published content, all 438 differential elements; mCODE 4.0.0 pairs 349, 227 identical, 339 complete, 472 of 473 differential elements; Plan-Net 1.2.0 (its package and US Core 3.1.1 fetched from the registry when the tests run) pairs 109, 78 identical, 99 complete, all 321 differential elements; HRex 1.1.0 (three US Core versions in context) pairs 46, 31 identical, all 46 complete, all 138 differential elements; Genomics Reporting 2.0.0 pairs 141, 113 identical, 129 complete, 254 of 259 differential elements. The decompiler is measured the same way: the published IPS and mCODE packages decompiled to FSH, compiled back and compared ("tests/gofsh-ips-test.rkt", "tests/gofsh-mcode-test.rkt") — all 117 IPS resources come back identical, 341 of 349 mCODE resources. The parser and the linter are measured against SUSHI’s own importer test suite ("tests/sushi-importer-test.rkt": 515 texts; 514 verdicts agree, no missed error, no over-report). The tests print every remaining difference, classified, largest first. The differences:

  • A few caret extensions on one IPS profile land in a different order (a url-keyed extension among [+]-indexed ones); a few mCODE examples whose published JSON differs from the tagged FSH sources; one element’s min; a UCUM unit with an annotation; in Plan-Net, instance details the test names. In Genomics Reporting, what the published package carries that its FSH does not: a SUSHI 2 representation of type-specific choice paths (Observation.valueQuantity as an element of its own), OperationDefinitions and examples that drifted after publication, coding versions the FSH never writes.

  • No ImplementationGuide resource, no narratives, no ActorDefinition conversion: these are publisher output.

  • Characteristics: and Context: metadata are parsed but not read (an extension’s context comes from a ^context caret). An insert of an unknown RuleSet is left unexpanded, not reported.

  • Snapshots are opt-in (--snapshot, emit-snapshot?); the default output is the differential. R4 and R5 only.

  • No code validation: a binding records its strength and value set, and check runs without a terminology service, so only bindings whose value set enumerates its codes are checked.

  • The decompiler gives idiomatic FSH for StructureDefinitions, ValueSets and CodeSystems; any other resource becomes a per-leaf Instance, and nothing is extracted into Aliases or RuleSets.

fsh/check🔗

 (require fsh/check) package: fsh

procedure

(check-fsh-project dir    
  [#:capability capability]) → check-report?
  dir : path-string?
  capability : (or/c string? #f) = #f
The project end to end: compile; validate every example against the project’s profiles in the same package context (the project’s own artifacts ahead of its dependencies and core); with a CapabilityStatement id, the generated server’s unmet requirements (loads fhir-server on demand). Every problem is a fhir/diagnostic positioned in the FSH: a validation issue is traced to the instance rule that wrote the element and names the profile rule it breaks. The project’s maps are checked against its structures in the same context (fml/project, on demand), their findings positioned in the map.
